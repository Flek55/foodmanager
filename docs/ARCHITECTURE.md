# Архитектура Foodmanager

## Требования

- Общий список покупок в реальном времени для семьи. Сервис многопользовательский:
  им пользуются несколько семей, и один человек может состоять в нескольких.
- Приглашение в семью по короткому коду.
- Учёт запасов: сначала ручные отметки «заканчивается» / «кончилось», затем прогноз по истории покупок.
- Любые товары: продукты, бытовая химия, аптека и т.д. Можно добавлять по штрихкоду
  или вручную, названием с описанием.
- Группировка списка по магазинам и категориям.
- Уведомления через Telegram-бота. Через него же можно добавлять товары в список.
- Вход: Google, логин с паролем, Telegram. Apple отложен, так как требует Apple Developer за $99 в год.
- Клиенты: PWA (iPhone, Android, веб) и Telegram Mini App на одной кодовой базе.
- Интерфейс на русском. Хостинг: сначала бесплатно или дёшево, затем зарубежный VPS.

## Схема

```
[React PWA / Mini App] ──REST──► [Go: API + бот + фоновые задачи] ──► [PostgreSQL]
      ▲ IndexedDB (офлайн)              │
      └────────── SSE ──────────────────┤
                                        ├──► Telegram Bot API
                                        └──► Open Food Facts
```

Всё это один Go-бинарник. В проде он запускается в Docker Compose вместе с Postgres и Caddy (HTTPS).
Переезд на другой сервер: скопировать compose-файл и дамп базы.

## Ключевые решения

| Решение | Почему |
|---|---|
| OpenAPI-first (oapi-codegen + openapi-typescript) | Фронт и бэк не разъезжаются, ошибки в контракте ловятся при компиляции |
| sqlc вместо ORM | Пишем обычный SQL, получаем типизированный Go-код |
| Миграции goose встроены в бинарник, применяются при старте | Не нужен отдельный шаг деплоя |
| Сессии в httpOnly cookie, в БД хранится только SHA-256 токена | Проще и безопаснее JWT для приложения на одном домене |
| UUIDv7 (`uuidv7()` в Postgres 18), клиент сам генерирует id | Можно создавать записи офлайн, повторная отправка не создаёт дубли |
| SSE вместо WebSocket | Нужен только канал сервер → клиент, SSE проще и сам переподключается |
| Telegram вместо Web Push | Web Push в PWA на iOS ненадёжен, а Telegram есть у всех |
| TypeScript 5.9, а не 7 | openapi-typescript использует JS-API компилятора, которого нет в нативном TS 7, а в peer-зависимостях у него только 5.x |
| sqlc запускается из Docker-образа | Не тянет в go.mod сотню зависимостей и не требует cgo на Windows |
| Если не участник семьи, ответ 404, а не 403 | По чужим id нельзя узнать, существует ли семья |
| CSRF: `http.CrossOriginProtection` + SameSite=Lax | Стандартная защита Go 1.25+ по заголовкам Sec-Fetch-Site/Origin, токены не нужны |
| Тесты с базой падают, а не пропускаются, если Postgres не запущен (`FOODMANAGER_SKIP_DB_TESTS=1` для явного пропуска) | Тихий пропуск однажды дал ложно-зелёный результат |
| Rate limit в памяти: вход 20/мин на IP и 5/мин на email, регистрация 20/мин на IP, инвайты 60/мин на IP | Защита от перебора паролей и кодов. Лимиты раздельные: семья из пяти человек с одного домашнего IP укладывается в них при знакомстве с приложением (есть тест). Для одного инстанса хранилища в памяти хватает |
| VPS за рубежом | Стабильный доступ к Telegram Bot API |
| Сборка образа на самом сервере (`update.sh`), без registry | Нет токенов и лишних сервисов. CI проверяет, что Dockerfile собирается |
| distroless-образ, healthcheck встроен в бинарник (`server -healthcheck`) | ~25 МБ, нет shell и curl, а значит и меньше поверхность атаки |
| IP клиента берётся из заголовков только при `TRUST_PROXY=true`, а Caddy перезаписывает `X-Real-IP` | Иначе rate limit обходился бы подделкой заголовка (есть тест) |
| SSE исключён из сжатия в Caddy | Компрессор буферизует ответ, и живые обновления приходили бы с задержкой |
| Нет `WriteTimeout` у `http.Server` | Он обрывал бы бесконечные SSE-потоки |

## Правила семей и инвайтов

- Создатель семьи становится её владельцем (`owner`), все остальные вступают как участники (`member`).
- Код приглашения: 8 символов из алфавита без похожих символов (без 0/O, 1/I/L), показывается как `K7QM-2XPA`.
  Регистр и дефис при вводе не важны.
- По умолчанию код действует 7 дней и на 10 вступлений (максимум 30 дней и 50 вступлений).
  Создать код может любой участник, отозвать тоже. Одновременно действует не больше 20 кодов.
- Повторное вступление человека, который уже в семье, ничего не меняет и не расходует использование кода.
- Переименовать семью и исключать участников может только владелец. Выйти может каждый.
  Если выходит последний владелец, права переходят к участнику, который в семье дольше всех.
  Если выходит последний человек, семья удаляется.
- Лимит: 30 участников в одной семье.
- Сессия живёт 30 дней с последней активности и продлевается не чаще раза в 12 часов.

## Список покупок

- Добавление по названию: товар ищется в справочнике семьи без учёта регистра.
  Если его нет, он создаётся с заглавной буквы, а категория угадывается по словарю основ
  (`shopping/guess.go`). Угаданную категорию достаточно один раз поправить вручную:
  дальше она запоминается за товаром.
- Один товар может быть в списке только один раз, пока его не купили (уникальный частичный индекс).
  Если добавить его повторно, обновится существующая позиция. Ответ при этом 200, а не 201,
  и интерфейс показывает «уже в списке».
- Повторный запрос с тем же клиентским `id` ничего не дублирует: это задел под офлайн-очередь.
- Купленное остаётся в разделе «В корзине», пока его не уберут.
- Магазины работают как фильтр: позиции без магазина видны в любом магазине,
  а новая позиция при выбранном фильтре сразу получает этот магазин.
- Любая запись идёт так: проверка членства → `BumpHouseholdVersion` (это же блокирует строку семьи,
  поэтому записи в одну семью выполняются по очереди и гонки get-or-create невозможны) → изменения → коммит →
  событие в SSE-хаб.
- Целостность между семьями обеспечивают составные внешние ключи `(household_id, x_id)`:
  сама база не позволит сослаться на магазин или товар чужой семьи.
- SSE: `GET /api/households/{id}/events` — обычный chi-хендлер, а не OpenAPI-операция.
  Сначала приходит `ready` с версией (по ней клиент после переподключения понимает, что что-то пропустил),
  затем `{"kind":"list","version":N}` или `{"kind":"household"}`, плюс ping каждые 25 секунд.
  Хаб хранится в памяти процесса. Если инстансов станет несколько, его заменит Postgres LISTEN/NOTIFY
  за тем же интерфейсом `events.Publisher`.

## Запасы дома и история покупок

- Запас хранится в товаре (`products.stock_status`): `ok` / `low` / `out`, а `NULL` значит, что за товаром не следят.
  Отдельная таблица не нужна, а изменения запаса бесплатно идут через дельта-синхронизацию и офлайн-очередь.
- Начать следить за товаром можно по названию на вкладке «Дома» (если товара нет, он создаётся,
  категория угадывается) или переключателем в шторке позиции списка.
- `low`/`out` сами добавляют товар в список, если его там нет. Клиент присылает id будущей позиции (`itemId`),
  а сервер всегда возвращает открытую позицию товара: новую или уже бывшую в списке.
  Так офлайн-очередь может ссылаться на позицию до синхронизации, и её id переадресуется, если сервер ответил другим.
- Отметка «куплено»:
  - пишет `purchase_events` (уникально по `item_id`, поэтому повторная отметка ничего не дублирует);
  - пересчитывает `purchase_count` и `last_purchased_at`;
  - отслеживаемому товару ставит `ok`.

  Снятие отметки удаляет событие. Статус запаса при этом не откатывается: прежний статус неизвестен.
- Купленные позиции уходят из списка через 12 часов (фоновая задача раз в 15 минут), а история остаётся.
- История товара (последние 20 покупок) запрашивается отдельно, когда открывают его шторку.
  В офлайн-снимок она не входит, потому что только растёт.

## Telegram

Бот (`internal/tgbot`) работает в том же процессе, что и API, через long polling.
Публичный адрес для вебхука ему не нужен, поэтому он одинаково запускается на ноутбуке и на сервере.
Клиент Bot API (`internal/telegram`) свой и минимальный. Токен вырезается из текстов ошибок,
потому что стандартные ошибки `net/http` печатают URL целиком, а токен входит в URL (есть тест).
Без `TELEGRAM_BOT_TOKEN`, или если Telegram недоступен при старте, приложение работает без бота.

- **Привязка.** «Подключить Telegram» в профиле → `t.me/<bot>?start=link_<токен>`.
  Токен одноразовый и живёт 15 минут. Один Telegram может быть привязан только к одному аккаунту.
- **Вход через бота** (без виджетов и настройки домена):
  1. страница получает `login_<токен>` (живёт 5 минут) и открывает бота;
  2. бот показывает «Войти? Запрос с: Edge на Windows» с кнопками «Да» и «Нет»;
  3. страница каждые 2 секунды опрашивает `/auth/telegram/complete`.

  Явное подтверждение обязательно: иначе злоумышленник прислал бы жертве свою ссылку и вошёл в её аккаунт.
  Незнакомому Telegram после подтверждения создаётся новый аккаунт без email и пароля.
- **Mini App.** Тот же фронт открывается в Telegram (кнопка меню бота регистрируется при старте, если есть https `PUBLIC_URL`).
  Telegram передаёт подписанные `initData` в хэше URL. Сервер проверяет HMAC от токена бота
  и срок давности (24 часа). Если Telegram не привязан, приложение предлагает
  создать аккаунт или войти по паролю, и после входа Telegram привязывается автоматически.
- **Добавление сообщением.** «молоко 2л, хлеб, яйца 10» → `SplitItems` + `ParseItem` (Go-копия фронтового разбора).
  Запятая между цифрами считается десятичной («Молоко 2,5%»). Если семей несколько,
  бот спрашивает, в какую добавлять, и запоминает выбор (`/family`).
- **`/list`.** Открытые позиции в порядке категорий, по кнопке на каждую. Нажатие «купил» отмечает позицию и перерисовывает сообщение.
- **Уведомления.** Сервис списка сообщает «добавлено» (только по-настоящему новые позиции, без повторов и слияний)
  и «стало мало/нет» (только при смене статуса). Нотификатор копит события семьи 90 секунд
  и шлёт каждому привязанному участнику одно сообщение о действиях **других**, с учётом его настроек.
  Если Telegram ответил 403 (бот заблокирован), участник помечается и пропускается, пока снова не напишет боту.
  Ожидающие сообщения досылаются при остановке сервера.

## Синхронизация и офлайн

**Сервер.** У каждой семьи есть счётчик `households.version`. Любая запись увеличивает его,
и изменённые строки получают этот номер в колонку `version`.
`GET /sync?since=N` отдаёт живые строки с `version > N` и id удалённых (tombstone).
Позиция списка содержит поля своего товара (название, категорию), поэтому
изменение товара или удаление категории тоже повышает `version` у затронутых позиций,
иначе дельта бы их не включила.

**Клиент** (`frontend/src/sync`): один движок `ListSync` на семью.

- `server` — последний подтверждённый сервером снимок с его версией.
- `outbox` — локальные операции, которые ещё не отправлены (add/update/check/delete/clearChecked, stock/track).
- На экране показывается `outbox`, применённый поверх `server` (`applyOp` повторяет серверные правила).
  Поэтому ответ сервера ничего «не перерисовывает», и при досинхронизации нет мигания.
- Оба состояния лежат в IndexedDB: список открывается мгновенно, а изменения переживают закрытие приложения.
- Раунд синхронизации: flush (отправить outbox по порядку) → pull (дельта с `since = server.version`).
  Раунды не пересекаются. Запускаются при старте, по событию `online`, при возврате на вкладку,
  по SSE-событию с версией новее нашей и по таймеру повтора (2 → 5 → 15 → 30 с).
- Ошибки:
  - нет сети, 5xx или 429 — пауза и повтор позже;
  - 401 или `household_not_found` — потерян доступ, приложение заново проверяет `me`;
  - остальные 4xx (валидация, 409, `item_not_found`) — операция выбрасывается с тостом,
    и на экране остаётся состояние сервера.
- Если сервер слил добавление с уже существующей позицией (ответил другим id),
  последующие операции в очереди переадресуются на этот id.
- Повторная отправка безопасна: add идемпотентен по клиентскому id,
  а delete считает 404 успехом.
- «Кто я и мои семьи» синхронно сохраняется в `localStorage` и восстанавливается до первого рендера
  (`lib/persist.ts`). Асинхронный persister от TanStack терял запись, если приложение сворачивали сразу после входа.
- Выход из аккаунта стирает с устройства всё: кэш, IndexedDB и очередь.

**PWA**: `public/manifest.webmanifest`, иконки (`public/icons`, мастер-файл `icon.svg`) и собственный `public/sw.js`
без плагинов (у vite-plugin-pwa может не быть совместимости с Vite 8, а здесь хватает 100 строк):

- навигация — сначала сеть, без сети отдаётся сохранённая копия;
- `/assets/*` — сначала кэш (в именах хеш содержимого);
- `/api` — никогда не кэшируется.

При установке service worker сам разбирает `index.html` и кэширует его ассеты,
поэтому офлайн работает уже после первого визита.
Go отдаёт `/assets/*` с `immutable`, а остальное с `no-cache`, так что обновления доходят сразу.
В dev-режиме (`make web`) service worker не регистрируется. Проверять PWA через `make preview`.

**Известные ограничения:**
- Без сети категория нового товара не угадывается: словарь живёт на сервере,
  поэтому до синхронизации товар лежит в «Без категории».
- Две вкладки одновременно делят IndexedDB и могут перезаписать очереди друг друга.
  Для PWA это редкий случай. Решение на будущее — Web Locks или BroadcastChannel.
- Магазины и категории редактируются только онлайн.

## Штрихкоды

- Сканирование камерой через пакет `barcode-detector` (zxing-wasm): форматы EAN-13/8, UPC, DataMatrix.
  Нужен он потому, что в Safari встроенного детектора нет.
- Из DataMatrix «Честного знака» берётся GTIN (AI `01`).
- Поиск идёт по порядку: каталог семьи → `global_products` → Open Food Facts.
  Если ничего не нашлось, пользователь вводит название, и оно сохраняется в `global_products`.
- Сценарии: «кончилось» (дома), «купил» (в магазине), «положил в запасы».

## Прогноз «пора купить»

Для товара нужно не меньше трёх покупок. Считается медиана интервала между ними.
Когда прошло около 90% интервала, а статус всё ещё `ok`, бот спрашивает, добавить ли товар в список.
Ответ «ещё есть» сдвигает прогноз.
